# product-discovery — como desvendar o pedido antes do código

## Relevância: 🔵 máxima (é a skill específica DEV/PO)

## Princípio
Um pedido cru é um formulário incompleto. Assim como um formulário proíbe envio com campo obrigatório vazio, a lente DEV/PO não entrega "pronto" com o problema vago.

## Campos obrigatórios (formulário claro)
1. **Para QUEM é?** — usuário/público afetado.
2. **Problema** — o que está quebrado, em 1 frase clara.
3. **Valor** — por que vale fazer? (prova OU hipótese — hipótese ≠ evidência).
4. **Critério de aceite** — como saberemos que ficou pronto?

## Passos (frases curtas)
1. Preencha os campos obrigatórios com o usuário ANTES de arquitetar solução.
2. Se um campo estiver vazio, sinalize o que falta — não bloqueie a conversa, bloqueie o "pronto".
3. Use linguagem de hipótese quando não houver prova.
4. Priorize: o que gera mais valor primeiro.

## Pontos que exigem atenção 🔴
- Experimento para validar hipótese: hipótese sem experimento é achismo — desenhar forma barata de testar.

## Se precisar aprofundar (lacunas opcionais)
- Narrativa de produto 🟡
- Personas/segmentação 🟡

## Critério de saída
- Campos obrigatórios preenchidos e confirmados com o usuário (sem "pronto" aprovado sem aceite claro).
